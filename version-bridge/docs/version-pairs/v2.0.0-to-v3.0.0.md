# Version Pair: v2.0.0 → v3.0.0

The first (and currently only) adjacent hop. Full lifecycle covered: `discover`, `select`, `init`, `confirm`, `status`, `cancel`, and their `on_*` callbacks.

## The v2.0.0 baseline — real, verified against `beckn2.yaml`

- `context.version` — real field, currently hard-locked (`const: 2.0.0`, line 2934). No `traceId` exists on `Context` today — confirmed by reading every field on the schema (lines 2907–3010): `action`, `version`, `bapId`, `senderId`, `bapUri`, `bppId`, `bppUri`, `receiverId`, `transactionId`, `messageId`, `networkId`, `timestamp`, `key`. No correlation-ID field beyond `transactionId`/`messageId`, neither of which serves the same purpose as a tracing ID.
- `Catalog` (the `on_discover` response body) has no summary/category-list field — confirmed against its real property list (`bppId`, `descriptor`, `isActive`, `provider`, `resources`, `offers`, `validity`).
- `Contract.performance[]` — real field (line 3082), each entry a `Performance` object with real fields `id`, `status`, `commitmentIds`, `performanceAttributes` (line 3418, confirmed `additionalProperties: false` — a closed schema, consistent with every other core object in this spec).

## The v3.0.0 delta — explicitly hypothetical, not a real published spec

No real "Beckn v3.0.0" exists. This is the illustrative scenario originally specified for this project:

| Change | v2.0.0 (real) | v3.0.0 (hypothetical) | Where it actually applies |
|---|---|---|---|
| New `context` field | *(absent)* | `traceId` | Every action's `context` — but see finding below |
| New `message` field | *(absent)* | `catalogSummary` | `on_discover` response only — `Catalog` has no analogous concept in any other action |
| Rename | `contract.performance[]` | `contract.progress[]` | Any action returning a `Contract` with a `performance` array — in this backend that's `on_confirm` and `on_status`; the other `on_*` artifacts handle it too, conditionally, since nothing in the schema stops a `Contract` from carrying `performance` elsewhere |

## A real finding from grounding this against the actual spec

None of the three changes affect a **request** payload, in any of the six actions:
- `discover`'s request body is `message.intent` — never touches `Contract` or `Catalog` at all.
- `select`/`init`/`confirm`/`status`/`cancel` requests carry a `contract`, but `performance` is PN-authored fulfillment data — a CN constructing a request has no reason to populate it, and this backend never does.
- `traceId`, being optional (per the original scenario constraint — "no mandatory field added"), is treated as **absent on the way up** rather than fabricated by the bridge. A v3.0.0 BPP's own code must already tolerate its absence, since it's optional by definition.

**Consequence**: all six request-direction artifacts (`{action}_from_v2.0.0_to_v3.0.0.jsonata`) are the JSONata identity function, `$` — there is genuinely nothing to change going from v2.0.0 to v3.0.0 on the request side. This mirrors a real finding from earlier in this project (the same conclusion was reached, independently, for a different pure-addition scenario) — worth stating plainly rather than manufacturing a transformation that isn't needed.

The six response-direction artifacts (`on_*`) all strip `traceId`; `on_discover` additionally strips `catalogSummary`, and every other `on_*` renames `progress` back to `performance` conditionally — only when the response actually carries one, since not every action's `Contract` does in this backend's current logic.
